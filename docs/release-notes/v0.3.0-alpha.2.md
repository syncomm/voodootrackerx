# VoodooTracker X v0.3.0-alpha.2 Release Notes

Release target: `v0.3.0-alpha.2`

Theme: Sample Lifecycle Alpha.

## Overview

VoodooTracker X `v0.3.0-alpha.2` is the Sample Lifecycle Alpha.

This release makes multisample instruments substantially safer and more useful
to edit. Samples can now be cleared in place, repopulated into exact empty
destinations, duplicated, moved, and swapped while preserving stable sample
identities and the instrument's canonical 96-note XM keymap.

The release also broadens practical legacy-XM editing through explicit exact /
normalized / unavailable editable-copy planning, hardens multi-pattern
song/order navigation, protects meaningful editable work from accidental New /
Open replacement, and closes release-gate reliability gaps found through
independent audit and maintainer musician testing.

## Highlights

- Clear represented samples in place without compacting later sample identities.
- Repopulate an exact canonical empty S01...S16 destination.
- Duplicate represented samples to the next tail identity without changing
  keymaps.
- Move and swap samples while preserving note-to-sound semantics.
- Preserve sparse sample-slot structure through XM export, reopen, and
  editable-copy workflows.
- Create normalized editable copies of supported legacy Linear-table XM files
  whose inert zero-payload sample-slot metadata cannot be preserved exactly.
- Keep `Make Editable Copy` actionable for unsupported loaded XM state and
  explain why conversion is unavailable.
- Navigate multi-pattern editable songs coherently from the main POS control and
  Song / Order editor, including empty allocated patterns.
- Follow POS and PTN correctly during live editable playback.
- Protect meaningful editable work before `File > New` / `Cmd+N` or
  `File > Open` / `Cmd+O` replaces it.
- Prevent concurrent WAV/M4A export presentation from creating a second export
  sheet or job.
- Make Clear Song Data stopped-only, confirmed, and immediately undoable for
  editable documents.

## Sample Lifecycle

### Stable sparse sample identities

Sample identities remain fixed in the S01...S16 namespace.

Clearing S02 does not renumber S03 or later samples. A cleared slot becomes an
honest `Empty destination`, while note-map references to that exact slot remain
in place and resolve unavailable until the slot is populated again.

Sparse sample layouts persist through supported XM export and reopen using
canonical empty-slot placeholders.

### Clear and repopulate

`Clear Sample` removes represented PCM and metadata from the selected sample
identity without compacting neighboring slots or silently remapping notes.

The same canonical empty destination can later be populated through LOAD or
SINE. Existing keymap assignments then become audible again through the
replacement sample at the same Sxx identity.

Clear and repopulate are separate one-edit transactions with exact immediate
Undo/Redo.

### Duplicate

`Duplicate Sample` copies a represented sample to the next tail identity after
the highest represented sample. Interior holes remain holes, and the instrument
keymap is not changed automatically.

### Move and Swap

`Edit > Move Sample…` provides insertion/shift semantics.

`Edit > Swap Sample…` performs pairwise exchange semantics.

Both operations transform sample identities, all 96 keymap references, and the
selected Sxx destination together in one transaction. Represented-to-empty
moves and swaps preserve unavailable routes rather than fabricating samples.

The goal is reference preservation: after a Move or Swap, the same mapped notes
continue resolving to the same represented sample content unless the user
explicitly remaps the instrument.

### Transaction safety

Lifecycle actions revalidate document identity, revision, selection, target,
transport, and operation state before committing. Cancelled, stale, invalid,
read-only, playing, same-slot, and no-op paths create no mutation or history.
Successful actions create one labeled edit with exact immediate Undo/Redo.

## Instrument Keymap Semantics

The canonical route remains:

```text
instrument + note
→ exact 96-note XM keymap
→ represented sample
```

The selected sample is editing focus only.

The first represented sample in a neutral instrument is mapped across all 96
notes as a creation-time bootstrap. Moving or swapping that content later moves
the keymap references with it; S01 is not permanently special.

The Instrument Editor ownership strip remains noninteractive display-only state.
Use `MAP RANGE…` for explicit note-range assignment.

The Sample Editor AUDITION control intentionally plays the selected represented
sample directly and does not consult the keymap.

## Legacy XM Editable Copies

Loaded modules remain read-only. `File > Make Editable Copy` is the explicit
transition into a new untitled editable document.

This release formalizes three loaded-XM outcomes:

```text
exact
normalized
unavailable
```

### Exact

Supported Linear-table XM state that fits the current editable boundary
transitions immediately to an editable copy.

### Normalized

Some legacy XM files contain zero-payload sample-slot header state that has no
effect on VTX playback but cannot be preserved exactly by the editable model.

For the approved Profile-v1 normalization, VTX can safely:

- preserve required empty Sxx identities;
- preserve every 96-note reference to those destinations;
- keep unavailable/silent routing intact;
- canonicalize inert empty-slot metadata;
- drop unreferenced trailing zero-payload slot provenance;
- preserve represented PCM, mappings, patterns, orders, timing, loops, and
  supported instrument state.

The original XM remains read-only and untouched.

A later exported XM may differ structurally from the original source. The
supported musical state is the preservation boundary; this is not a promise of
arbitrary-XM lossless or byte-identical round trip.

### Unavailable

If VTX can play a module but cannot safely preserve its represented editable
state, `Make Editable Copy` remains actionable and explains why the operation is
unavailable instead of silently appearing disabled.

Current examples include Amiga-frequency-table XM and unsupported represented
loop or instrument state. VTX does not silently convert Amiga frequency mode to
Linear.

## Song / Order Reliability

From-scratch editable documents now use one canonical stopped navigation
authority. The main-window POS control and Song / Order selection stay coherent
across multiple orders and patterns, including blank allocated patterns that do
not yet contain events.

For example:

```text
ORD 000 → P000
ORD 001 → P001
ORD 002 → P002
```

can be navigated:

```text
POS 0 → 1 → 2 → 1 → 0
```

without editable-document snap-back.

Pattern viewing remains intentionally distinct from order selection:

- normal Play follows the selected POS/order;
- Play Current Pattern follows the displayed pattern;
- viewing another pattern does not silently reassign the selected order.

During live editable song playback, POS and PTN follow order transitions
together in real time. Stop reconciles the final playback position back into the
stopped editable navigation state.

## Safety and Reliability

### Document-replacement safety

For a non-pristine editable song, `File > New` / `Cmd+N` and `File > Open` /
`Cmd+O` ask before replacing meaningful work. Cancel preserves the current
document, identity, revision, and undo history.

For Open, confirming the warning does not discard the song merely because the
file chooser was shown: chooser cancellation or load failure leaves the editable
document intact. Pristine new documents and loaded read-only modules retain the
low-friction behavior and do not receive unnecessary discard warnings.

Save and Save As remain intentionally disabled; Export XM is still the current
persistence workflow.

### Clear Song Data

`Clear Song Data` requires stopped transport and explicit confirmation. For
editable documents, confirmation clears pattern/order data while preserving the
instrument/sample palette and creates one immediate Undo action. Cancel, stale
state, playback, and no-op paths create no mutation or history. The Song / Order
editor and application menu use the same safety contract.

### Audio-export re-entry

Only one WAV/M4A export presentation may be active at a time:

```text
WAV active → WAV disabled
WAV active → M4A disabled
M4A active → WAV disabled
M4A active → M4A disabled
```

Direct and stale action paths are guarded, so a second progress sheet or render
job cannot replace the active export presentation. Availability returns after
success, failure, or cancellation.

### Other release-gate remediation

- Clear Sample confirmation now promises only the immediate Undo behavior the
  app guarantees.
- Third-party-derived placeholder app-icon resources and build references were
  removed; this release uses default macOS app-icon behavior without adding
  replacement artwork.
- A targeted tracker viewport test-honesty correction now exercises production
  geometry and removes a contradictory test-local selector specification.

## XM Export / Round Trip

The supported lifecycle gate exercises:

```text
editable document
→ sample lifecycle edits
→ Export XM
→ reopen
→ Make Editable Copy where supported
→ re-export
```

Coverage includes:

- sparse represented/empty sample identities;
- exact 96-note keymaps;
- sample PCM and controls;
- loops;
- instrument envelopes, fadeout, and autovibrato;
- patterns, orders, and timing;
- normalized editable-copy semantics.

For canonical VTX-authored state, deterministic re-export remains expected where
the current writer contract promises it.

For normalized legacy copies, compare the normalized editable state with the
reopened normalized export semantically, not the exported bytes with the
original legacy source.

The final Sample Lifecycle Alpha gate verdict is **GO**.

Validation covered the complete SwiftPM, macOS Xcode, and Python suites;

Release build; and a universal `arm64 + x86_64` Release build. Maintainer

counts or identities.

## Known Alpha Limitations

- Save and Save As remain disabled. Export XM is the persistence boundary.
- Loaded modules remain read-only.
- Some loaded XM state can be played but cannot yet be made editable when VTX
  cannot prove safe semantic preservation.
- Native editable Amiga-frequency-table support is deferred. Amiga XM can be
  played, but VTX does not silently convert it to Linear for editing.
- Graphical keymap assignment remains deferred; use `MAP RANGE…`.
- Broader destructive waveform editing remains deferred.
- MIDI input is not part of this release.
- XI interchange remains deferred.
- Broader settings and UI work remains future work.
- Playback/effect and real-time callback correctness work remains scheduled for
  focused post-alpha tranches.
- AUv3 remains post-v1.
